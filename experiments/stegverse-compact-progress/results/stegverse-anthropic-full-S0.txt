## 1. Task Parsing

**Source problem (verbatim core):**
> The evaluator returns ALLOW exactly when GBP and BD and OC all hold.

**Entities identified:**

| Symbol | Role | Type |
|--------|------|------|
| `GBP` | Predicate on a candidate transition | `T → Prop` |
| `BD` | Predicate on a candidate transition | `T → Prop` |
| `OC` | Predicate on a candidate transition | `T → Prop` |
| `ALLOW` | Output predicate on a candidate transition | `T → Prop` |
| `t` | Candidate transition (universally quantified) | `T` |

**Logical reading of the problem statement:**

The evaluator's behaviour is fully specified by the single biconditional:

> For all candidate transitions `t`: `ALLOW(t)` holds **if and only if** `GBP(t)` holds **and** `BD(t)` holds **and** `OC(t)` holds.

This is a **necessary-and-sufficient characterisation** (biconditional, not merely a sufficient condition or necessary condition alone).

---

## 2. Stipulations (Given, Not Derived)

**S1.** `T` is an arbitrary type representing candidate transitions. No further structure on `T` is assumed.

**S2.** `GBP`, `BD`, `OC`, and `ALLOW` are predicates of type `T → Prop`. They are abstract; no computational definition is supplied or assumed.

**S3.** The evaluator specification is taken as axiomatic for this experiment: `ALLOW t ↔ GBP t ∧ BD t ∧ OC t`.

**S4.** No claim is made that any deployed GCAT/BCAT implementation satisfies S3. The characterisation is of an *abstract evaluator* defined solely by S3.

**S5.** The Lean 4 artifact targets only the logical core (the biconditional and its immediate consequences). It does not target any runtime system.
