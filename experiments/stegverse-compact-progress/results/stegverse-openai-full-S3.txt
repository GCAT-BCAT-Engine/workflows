**Stipulated setting**
Let `Transition` be an arbitrary type, with predicates:

- `GBP : Transition → Prop`
- `BD : Transition → Prop`
- `OC : Transition → Prop`
- `ALLOW : Transition → Prop`

Assume:

`allow_spec : ∀ t : Transition, ALLOW(t) ↔ (GBP(t) ∧ BD(t) ∧ OC(t))`.

**Generated proof strategy**
For an arbitrary `t : Transition`, instantiate `allow_spec` at `t`. The resulting equivalence directly supplies both required directions:

1. **Necessity lemma**
   - Input: `hAllow : ALLOW(t)`.
   - Use the forward implication of `allow_spec t`.
   - Output: `GBP(t) ∧ BD(t) ∧ OC(t)`.

2. **Sufficiency lemma**
   - Input: `hConditions : GBP(t) ∧ BD(t) ∧ OC(t)`.
   - Use the reverse implication of `allow_spec t`.
   - Output: `ALLOW(t)`.

3. **Characterization theorem**
   - Construct the biconditional from the necessity and sufficiency lemmas.
   - Alternatively, return `allow_spec t` directly because its instantiated type is exactly the target theorem.

No auxiliary assumptions such as decidability, predicate independence, excluded middle, or domain-specific GCAT/BCAT semantics are needed.

**Lemma decomposition**
The logical dependency structure is:

```text
allow_spec t
 ├─ forward direction ─→ allow_necessity t
 └─ reverse direction ─→ allow_sufficiency t

allow_necessity t + allow_sufficiency t
 └─→ allow_admissible_iff t
```

The conjunction is parsed as:

`GBP t ∧ (BD t ∧ OC t)`,

which is Lean’s standard right-associative interpretation of `GBP t ∧ BD t ∧ OC t`. No reassociation is required because the assumption and conclusions use the same expression.
